## Implementación

### `src/providers/theme-provider.tsx` (nuevo)

Context de React (`ThemeContext`) + `ThemeProvider`. Justificación de la
abstracción (skill `architecture`): hay más de un consumidor real
(`ThemeToggle` hoy, cualquier componente futuro que necesite leer el tema) y
el propio criterio de aceptación pide que el estado de tema sea compartido
entre layout y componentes — no es una interfaz especulativa.

`readResolvedTheme()` lee el atributo `data-theme` que ya fijó el script
inline de `layout.tsx` **en el inicializador perezoso de `useState`**, no en
un `useEffect` — evita el error de lint
`react-hooks/set-state-in-effect` ("Calling setState synchronously within an
effect can trigger cascading renders") que el propio `eslint-config-next` del
repo bloqueaba, y evita además un re-render extra tras montar.

`setTheme`/`toggleTheme` aplican el atributo `data-theme` sobre
`document.documentElement` y persisten en `localStorage`
(`miattv-theme`, `THEME_STORAGE_KEY` exportado como fuente única de verdad,
reutilizado también por el script inline del layout).

### `src/hooks/use-theme.ts` (nuevo)

`useTheme()` consume `ThemeContext`; lanza si se usa fuera del provider
(mismo patrón defensivo que evita estados inconsistentes silenciosos).

### `src/themes/theme.css` (nuevo)

Variables (`--background`, `--foreground`, `--surface`, `--border`,
`--accent`, `--accent-foreground`) en tres capas:
- `:root` sin atributo: valores claros por defecto (fallback sin JS).
- `@media (prefers-color-scheme: dark)` sobre `:root` sin atributo: respeta
  la preferencia de sistema mientras no haya tema resuelto por JS/atributo.
- `:root[data-theme='light']` / `:root[data-theme='dark']`: fuente de verdad
  una vez que el script inline (o el toggle) resuelve el tema; el selector
  con atributo tiene mayor especificidad que el `:root` a secas, así que
  siempre gana sobre el fallback de media query.

Los valores claros/oscuros son los mismos que ya usaba `globals.css` con
media query (`#ffffff`/`#171717` y `#0a0a0a`/`#ededed`) — no se inventó una
paleta nueva, solo se reorganizó por atributo en vez de solo por media query.

### `src/components/ui/theme-toggle/ThemeToggle.tsx` + `.module.css` (nuevo)

Botón nativo (`<button>`, sin reinventar semántica), texto visible que
declara el estado ("Modo claro" / "Modo oscuro" — no depende solo de un
icono/color), `aria-pressed` como en `LanguageSwitcher` de EX-17 para
mantener el mismo patrón de toggle accesible en el repo. `focus-visible`
explícito con `outline` en `--accent` (nunca se quitó el outline nativo sin
sustituirlo).

`suppressHydrationWarning` en el botón: el texto depende del tema resuelto en
cliente (localStorage/preferencia de sistema), que el servidor no puede
conocer — mismatch intencional y controlado (uso documentado de
`suppressHydrationWarning` en React), no un bug oculto.

### `src/app/layout.tsx`

- `<html lang="es" suppressHydrationWarning>`: necesario porque el script
  inline fija `data-theme` en `<html>` antes de hidratar, difiere del HTML
  servido por el servidor (que no puede conocer el tema). `suppressHydrationWarning`
  en un elemento solo silencia el propio elemento, no sus hijos.
- `<Script id="theme-init" strategy="beforeInteractive">`: Next.js inyecta
  scripts `beforeInteractive` en el `<head>` del HTML inicial y los ejecuta
  antes de pintar/hidratar, evitando el flash de tema incorrecto (FOUC) sin
  añadir `next-themes` ni ninguna dependencia nueva. Contenido 100% estático
  (interpola `THEME_STORAGE_KEY`, una constante propia, no input de usuario)
  — sin riesgo de inyección.
- `ThemeProvider` envuelve `children`; `ThemeToggle` se renderiza en el
  layout raíz (visible en toda la app, mismo criterio que `LanguageSwitcher`
  en el WIP de EX-17).

### `src/app/globals.css`

`@import '../themes/theme.css'` sustituye a las variables `:root`/media query
que antes vivían aquí duplicadas; añadido `color-scheme` por atributo
(`[data-theme='dark']`/`[data-theme='light']`) con fallback de media query
para controles nativos del navegador (scrollbars, inputs) cuando aún no hay
atributo resuelto.

`src/app/page.tsx` no se tocó: el plan no lo requería y no aporta contenido
sensible al tema fuera de lo que ya cubren las variables CSS globales.

## Iteración 2 — corrección de bloqueo de `qa`

Plan publicado en Jira (comentario `10186`, EX-18). `qa` bloqueó la
iteración 1 por tres hallazgos, todos con la misma causa raíz: `layout.tsx`
(Server Component) interpolaba `THEME_STORAGE_KEY` importado desde
`theme-provider.tsx` (`'use client'`) dentro del script inline
`beforeInteractive` — Next.js sustituye ese export por una referencia de
cliente inválida al interpolarla en HTML servido, rompiendo el script en
runtime.

### Causa raíz (hallazgos #1 y #2 de `qa`)

- `src/themes/constants.ts` (nuevo, módulo plano SIN `'use client'`): única
  fuente de verdad de `THEME_STORAGE_KEY = 'miattv-theme'`.
- `src/providers/theme-provider.tsx`: deja de declarar/exportar la
  constante; ahora la importa desde `@theme/constants`.
- `src/app/layout.tsx`: importa `THEME_STORAGE_KEY` directamente desde
  `@theme/constants` (no desde el provider cliente) para el script inline.
- Verificado contra el HTML servido en `npm run start` (puerto 4123, curl a
  `/`): el script `#theme-init` contiene el literal `'miattv-theme'`
  (`localStorage.getItem('miattv-theme')`), no una referencia de cliente
  rota. `data-theme` queda fijado en `<html>` antes de hidratar.
  `aria-pressed` de `ThemeToggle` deriva de `useTheme()` (que lee
  `data-theme` en el inicializador perezoso de `useState`, sin cambios en
  esta iteración) — al dejar de romper el script, queda sincronizado con el
  tema realmente pintado.

### Alcance ampliado (hallazgo #3 de `qa`): `page.tsx`/`page.module.css`

- `src/themes/theme.css`: se añadieron `--text-primary`, `--text-secondary`,

- `src/app/page.module.css`: eliminadas las declaraciones locales

### Fix adicional: `aria-pressed` desincronizado (hallazgo de `qa`, iteración anterior)

Causa raíz confirmada de forma reproducible con un harness de hidratación
propio (`react-dom/server` + `react-dom/client` sobre `jsdom`, fuera del
repo, en el scratchpad de esta sesión): el `useState` con inicializador
perezoso de `theme-provider.tsx` sí computaba el tema correcto en cliente
durante la hidratación, pero como el texto/`aria-pressed` del botón difieren
del HTML servido (el servidor no puede conocer el tema persistido) y el
elemento lleva `suppressHydrationWarning`, React silenciaba el aviso **sin
corregir el DOM** — `aria-pressed` y el texto quedaban congelados en el
valor servido por el servidor (`false`/"Modo claro") hasta el primer click,
aunque el resto de la página (controlado por CSS vía el atributo
`data-theme`, fijado imperativamente por el script inline) sí mostraba el
tema correcto. Reproducido exactamente ese mismatch en el harness antes del
fix.

Fix: `src/providers/theme-provider.tsx` pasa de `useState` a
`useSyncExternalStore` (`getSnapshot`/`getServerSnapshot` leyendo/asumiendo
el atributo `data-theme`, `subscribe` vía `MutationObserver` sobre ese mismo
atributo). Es la alternativa que recomienda explícitamente el propio lint
`react-hooks/set-state-in-effect` para "force update / external sync" — no
requiere `setState` dentro de un efecto (evita reintroducir el error de
lint que motivó el `useState` perezoso en la iteración 1) y, a diferencia de
él, garantiza una re-sincronización real justo tras hidratar. Verificado en
el mismo harness: con `useSyncExternalStore`, tras hidratar con
`data-theme="dark"` ya fijado (preferencia persistida simulada),
`aria-pressed` pasa a `"true"` y el texto a "Modo oscuro" sin intervención
del usuario; y una mutación posterior del atributo (simulando el click de
`toggleTheme`) también se refleja correctamente vía el `MutationObserver`.
`setTheme`/`toggleTheme` ahora mutan el DOM directamente (`applyTheme`) sin
guardar duplicado en `useState`, ya que `data-theme` es la única fuente de
verdad.
