## Implementación

### Dependencia

```
npm install next-intl@4.13.4
```

Versión con soporte explícito de peer deps para `next@^16.0.0` y
`react@^19.0.0` (verificado con `npm view next-intl peerDependencies` antes
de instalar — el repo ya usa `next 16.2.11` / `react 19.2.4`). No duplica
ninguna librería de i18n ya presente (no había ninguna).

### `next.config.ts`

Envuelto con `createNextIntlPlugin()` (sin argumento: el plugin resuelve por
defecto `./src/i18n/request.ts`, que es donde vive el request config de este
repo — verificado en el propio código del plugin instalado, no asumido).

### `src/i18n/routing.ts`

Whitelist de locales (`es`, `en`), `defaultLocale = 'es'` (coherente con el
`lang="es"` que ya tenía `layout.tsx` desde EX-16) y el nombre de la cookie
(`NEXT_LOCALE`, el nombre convencional de next-intl). Type guard `isLocale`
usado tanto en el request config del servidor como en el hook del cliente
— es la única puerta de validación de un valor que viene de una cookie
(entrada no confiable).

### `src/i18n/request.ts`

Lee la cookie `NEXT_LOCALE`, la valida contra la whitelist con `isLocale`
antes de usarla para el `import()` dinámico de
`./locales/${locale}.json` — sin esa validación, un valor de cookie
arbitrario habría permitido un intento de path traversal / lectura de
archivo fuera de lo previsto en el `import()` dinámico (ver autorevisión de
`security` más abajo). Si la cookie falta o no es válida, cae a
`defaultLocale`.

No hay middleware de reescritura de ruta (decisión de arquitectura del
plan): el locale nunca sale de la cookie/request config.

### `src/i18n/locales/{es,en}.json`

Namespace `Home` (contenido migrado de `page.tsx`, incluyendo el `alt` de
las imágenes) y `LanguageSwitcher` (`groupLabel` traducido; los nombres de
idioma `es`/`en` son autónimos — "Español"/"English" en ambos archivos, no
se traducen entre sí para no generar confusión al togglear).

### `src/providers/i18n-provider.tsx`

Server Component fino que envuelve `NextIntlClientProvider` de `next-intl`
— en Server Components, `next-intl` inyecta locale/mensajes automáticamente
desde el request config, no hace falta pasarlos a mano (verificado en los
tipos del paquete: la variante `react-server` de `NextIntlClientProvider` es
async y los resuelve ella misma).

### `src/hooks/useLocaleSwitcher.ts`

Hook de cliente (`'use client'`): expone `locale` actual (vía `useLocale()`
de `next-intl`), y `setLocale(nextLocale)` que escribe la cookie
(`path=/`, `max-age` 1 año, `SameSite=Lax` — no es dato sensible, no
necesita `httpOnly` porque el propio cliente tiene que poder escribirla) y
llama a `router.refresh()` dentro de `startTransition` para revalidar los
Server Components con el nuevo locale, sin navegar ni tocar el path.

### `src/components/features/language-switcher/LanguageSwitcher.tsx`

Grupo de dos botones nativos (`<button>`, no `div` con `onClick`) con
`role="group"` + `aria-label` traducido, `aria-pressed`/`aria-current` para
comunicar el idioma activo a lectores de pantalla, y `disabled` durante el
refresh en curso (evita doble submit). Montado en `src/app/layout.tsx`
(dentro de `I18nProvider`, junto al `children`) para que esté visible en
todas las páginas — un componente de feature sin ningún sitio que lo
renderice habría sido código muerto.

### `src/app/layout.tsx`

`lang="es"` hardcodeado → `lang={await getLocale()}` (`next-intl/server`).
El layout pasa a ser un Server Component async. Envuelve `children` (y el
propio `LanguageSwitcher`) en `I18nProvider`.

### `src/app/page.tsx`

Contenido migrado a `useTranslations('Home')`. El párrafo con los dos
enlaces (`Templates`/`Learning`) usa `t.rich(...)` con los componentes de
enlace inyectados como children — mantiene el mismo markup/atributos
(`target="_blank"`, `rel="noopener noreferrer"`) que tenía antes, ahora con
el texto traducido.

## Gate de calidad

### Autorevisión (`security` / `performance` / `accessibility` AA)

- `security`: superficie relevante es la cookie `NEXT_LOCALE`, que es un
  input no confiable — validada contra whitelist (`isLocale`) antes de
  usarse en el `import()` dinámico del catálogo de mensajes, evitando un
  path traversal. No hay credenciales ni datos sensibles en el diff. La
  cookie no es `httpOnly` a propósito (debe poder escribirla el cliente) y
  no guarda nada sensible (solo `es`/`en`), así que no aplica cifrado ni
  restricción adicional.
- `performance`: sin queries, listados ni llamadas de red nuevas. Único
  efecto medible: la home deja de poder pre-renderizarse como estática
  (`next build` la marca `ƒ` en vez de `○`) porque el request config lee
  `cookies()` en cada petición — es una consecuencia directa e inevitable de
  la decisión de arquitectura "locale por cookie, no por ruta" del plan
  (una ruta estática no puede leer cookies por request), no un patrón de
  N+1 ni una query cara. Señalado aquí porque es un trade-off real, no
  porque sea un hallazgo a corregir.
- `accessibility` (AA, `repos[].accessibility.level`): botones nativos
  (operables por teclado sin nada adicional), `role="group"` +
  `aria-label` traducido, `aria-pressed`/`aria-current` para el estado
  activo, `disabled` nativo durante el refresh. Sin `outline` removido en
  ningún selector (foco visible intacto). Contraste del switcher reutiliza
  `--foreground`/`--background` del propio tema (ya usados en el resto del
  sitio, cumplen 4.5:1). `lang` del documento ahora dinámico según el
  locale real.

## Iteración 2 — corrección tras fallo de `qa`

`qa` reportó que el default de idioma no negociaba `Accept-Language`: al no
haber cookie `NEXT_LOCALE` todavía, `src/i18n/request.ts` caía siempre a
`defaultLocale = 'es'` sin mirar la preferencia real del navegador. Plan
completo publicado como comentario en el ticket EX-17 (Jira); se continuó
sobre el WIP existente de la rama `feature/EX-17-i18n-en-es`, sin
reiniciarla.

### `src/proxy.ts` (negociación de `Accept-Language`)

El plan pedía `src/middleware.ts`. Antes de crearlo se verificó el build en
Next.js 16.2.11 (ya instalado en el repo desde EX-16): la convención
`middleware.<ext>` está deprecada en esta versión a favor de `proxy.<ext>`
(`next build` lo marca explícitamente: *"The 'middleware' file convention is
deprecated. Please use 'proxy' instead"*, ver
`node_modules/next/dist/docs/01-app/02-guides/upgrading/codemods.md`,
codemod `middleware-to-proxy`). Mismo comportamiento, mismo `config.matcher`,
solo cambia el nombre del archivo y de la función exportada
(`middleware` → `proxy`) — se usó `proxy.ts` para no introducir un warning
de deprecación evitable en un repo que arranca desde cero con Next 16.

- `matcher: ['/((?!_next|api|.*\\..*).*)']` — excluye `_next`, `api` y
  cualquier ruta con extensión (estáticos).
- Si la request ya trae cookie `NEXT_LOCALE` con un valor de la whitelist
  (`isLocale`), no hace nada (`NextResponse.next()`) — la cookie manda.
- Si no, parsea `Accept-Language` con un parser propio (sin dependencia
  nueva: solo 2 locales) que separa tags y q-values, descarta `q=0`, ordena
  por calidad descendente y decide `es` si algún tag preferido empieza por
  `es`, `en` (=`defaultLocale`) en cualquier otro caso — incluida ausencia
  total del header.
- Fija la cookie en dos sitios: `request.cookies.set(...)` +
  `NextResponse.next({ request: { headers: request.headers } })` para que el
  request config de `next-intl` (que lee `cookies()` del propio request) ya
  vea el locale negociado en esta misma petición, y
  `response.cookies.set(...)` (`path=/`, `max-age` 1 año, `SameSite=Lax`,
  igual que en `useLocaleSwitcher`) para que persista en el navegador.

### `src/i18n/routing.ts`

`defaultLocale`: `'es'` → `'en'`. Coherente con "español si el navegador lo
pide, inglés en cualquier otro caso" — el fallback final (sin cookie, sin
`Accept-Language`, o con un `Accept-Language` que no pide español) ya no
puede ser una decisión distinta según si la lee el proxy o el request
config; ambos comparten la misma constante.

### `src/i18n/request.ts`

Sin cambio de lógica (la lectura de cookie + fallback a `defaultLocale`
pasa a ser red de seguridad para requests que no pasaron por el proxy —
p. ej. un fetch directo a una ruta ya cacheada — no el mecanismo principal
de negociación). Único cambio: el `import()` dinámico apunta a
`./local/${locale}.json` tras el rename de carpeta (ver debajo).

### Rename `src/i18n/locales/` → `src/i18n/local/`

`mv` de `es.json`/`en.json` (no había commit previo que preservar con
`git mv`, la carpeta seguía untracked de la iteración 1). Coincide con lo
que pide literalmente la descripción del ticket
(`/i18n/local/[locale].json`). Única referencia a actualizar: el `import()`
dinámico en `request.ts` (arriba). `LanguageSwitcher`, `useLocaleSwitcher` y
el resto de módulos de i18n usan los namespaces vía `useTranslations`/
`getRequestConfig`, no la ruta del archivo, así que no tenían nada que
tocar.

### `src/app/layout.tsx`

Sin cambios en esta iteración — sigue usando `lang={await getLocale()}`
(ya dinámico desde la iteración 1). Verificado que el `lang` del documento
sigue siendo correcto con la negociación nueva: `getLocale()` lee el
request config, que a su vez lee la cookie que el proxy ya dejó fijada en
el propio request antes de que el Server Component se renderice — no hay
ventana en la que `lang` y el contenido negociado diverjan.

## Gate de calidad (iteración 2)

### Autorevisión (`security` / `performance` / `accessibility` AA)

- `security`: `Accept-Language` es input no confiable — nunca se usa el
  valor crudo del header más allá de un `.startsWith('es')` para decidir
  entre los 2 valores whitelisteados; el resultado siempre es literalmente
  `'es'` o `defaultLocale` (`'en'`), nunca el string del header en sí. No se
  interpola en el `import()` dinámico (eso lo sigue validando `isLocale`
  en `request.ts`, sin cambios). Sin dependencias nuevas (parser propio, tal
  como pedía el plan). Cookie sin cambios de política respecto a la
  iteración 1 (no sensible, no `httpOnly`).
- `performance`: el proxy corre en el edge antes de cualquier render;
  parsear un header de tamaño acotado (unos pocos tags) no es una operación
  cara, y solo ocurre cuando falta la cookie (primera visita), no en cada
  request. Sin queries, listados ni llamadas de red nuevas. La home sigue
  sin poder pre-renderizarse como estática (`ƒ /` en el build), consecuencia
  ya señalada en la iteración 1, no un cambio nuevo de esta iteración.
- `accessibility` (AA): el cambio es de negociación de idioma en el proxy,
  sin superficie visual propia. Confirmado que `lang` del documento sigue
  siendo dinámico y coherente con el contenido (ver sección de
  `layout.tsx` arriba) — es el único punto de contacto real entre esta
  iteración y accesibilidad, y no se ha degradado.
